{# Amazon Easy Ship orders, as the WAREHOUSE reads them: today's dispatch. Asked for: "Lets show them only the data which is waiting for pickup. Rest of the orders are the responsibility of the ecom team to ship on portal" … "Each parent item total weight orders … uske niche 500g, 1kg - kitne kitne units. sort it total weight wise" … "user should be able to put how many units has he packed against each sku." Six things are deliberate: 1. **Today's dispatch is the default and, for ops, the only view.** An order still in `Unshipped` belongs to the ecom team, who ship it on Seller Central; putting it here asks the floor to box something with no label. The owner's four-section picking sheet is still reachable, but only for an administrator. 2. **A dispatched order does NOT leave the list.** Measured on production: 200 of 264 orders flipped from `PendingPickUp` to `PickedUp` overnight. Keyed on "not yet collected" this screen would empty itself through the day and take the packed tally with it, so the rule is ship-by == today AND labelled. 3. **Parent product, then pack sizes beneath, heaviest first.** Weight is what fills the vehicle. Sizes never collapse — 500 g and 1 kg live on different shelves — but they roll up, because "how much ABC Sattu today" is the question being asked. 4. **Packed units are OURS.** Amazon does not know how many units are in a box on this floor. Typing here writes no status, raises no invoice and contradicts nothing. 5. **Over-packing warns and never blocks.** The boxes physically exist; refusing the entry would leave real stock unrecorded. Same rule as `logic.over_packed`. 6. **Every time is IST.** Amazon sends 18:29Z = 23:59 IST, end of day in India. The server converts; this page never does. `dateIST` splits the string rather than parsing it, because `new Date("2026-08-25")` is UTC midnight and rendered 05:30 the NEXT morning in the column the warehouse plans against. #}
