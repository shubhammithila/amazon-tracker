{# Today's dispatch, in three tabs over the same 264-order day. Asked for: "lets make three tabs. 1) for the total weight thing of all the parents … put available weight of stock … calculate weight of stock to be purchased. 2) sku wise total orders … available qty, packed qty … 3) all orders with order id, sku, qty, item name, item weight, destination, amazon status." It was ONE table and it read as haphazard. Measured before redesigning: 101 rows and 7 columns, UNITS == ORDERS on 57 of 68 size rows, 7 of 33 products whose parent row was an identical twin of its only size row, and 41 of 68 rows holding three units or fewer. The longest product name is 29 characters, so width was never the constraint — the screen was answering three different questions at once. Seven things are deliberate: 1. **Three tabs, split by QUESTION.** Weight and purchasing (the owner, buying), per-SKU packing (the floor, entering), the order list (reconciliation). One tab is editable at a time in practice, and each has its own search box. 2. **Tab 1's stock is RAW MATERIAL in kilograms, and it is standing.** Easy Ship orders are packed the same day, so nothing is packed in advance: what is on the shelf is raw. It has no date — a dated field would be blank every morning and this tab would read "buy everything" at 9am daily. 3. **Tab 2 is FLAT.** No parent rows: the product name repeats per row, because with 68 rows in the existing sort order there is no grouping to lean on, and a parent row whose only child carries the same numbers is the noise this redesign removed. 4. **A dispatched order does NOT leave the list.** Measured: 200 of 264 orders flipped from `PendingPickUp` to `PickedUp` overnight. Keyed on "not yet collected" this screen would empty itself through the day and take the packed tally with it. 5. **Tab 3 keeps itself current** — the scheduled job refreshes from Amazon every 30 minutes and this page re-reads LOCAL rows every 60 seconds. It re-renders tab 3 ONLY: redrawing a tab with number boxes would discard whatever was being typed. 6. **Over-packing warns and never blocks.** The boxes physically exist; refusing the entry would leave real stock unrecorded. Same rule as `logic.over_packed`. 7. **Every time is IST.** `dateIST` splits the string rather than parsing it, because `new Date("2026-08-25")` is UTC midnight and rendered 05:30 the NEXT morning in the column the warehouse plans against. #}
